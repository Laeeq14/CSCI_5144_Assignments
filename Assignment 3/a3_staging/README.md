# Assignment 3 -- Distributed Key-Value Store with Consistent Hashing

**Course:** CSCI 5144 -- Cloud Computing

---

## 1. Objective

This assignment extends the single-node KV store from Assignment 2 into a distributed cluster of up to three nodes. Load is distributed across nodes using consistent hashing, and each node runs in its own Docker container. Performance is measured at one, two, and three nodes to evaluate how throughput and latency change as the cluster grows.

---

## 2. Architecture

```
Client
  |
  v
proxy (port 8000)  --  consistent hash ring (SHA-256, 100 virtual nodes per backend)
  |
  +-- kv1:8080  (host port 8081)
  +-- kv2:8080  (host port 8082)
  +-- kv3:8080  (host port 8083)
```

The proxy is a lightweight Go HTTP reverse proxy. It routes every GET, POST, and DELETE request to the correct backend based on a deterministic hash of the key. The KV store nodes are identical to the Assignment 2 server: an in-memory map protected by a read-write mutex, with async disk persistence and graceful shutdown.

---

## 3. Consistent Hashing

Consistent hashing ensures that adding or removing a node only remaps approximately 1/N of keys, rather than all keys as modulo hashing would. The implementation uses SHA-256 to place 100 virtual nodes per backend on a 2^64 ring. To route a key, the proxy hashes the key with SHA-256, binary-searches for the first ring position greater than or equal to the key hash, and forwards the request to the corresponding backend. If the key hash exceeds all ring positions, it wraps to the first entry.

The ring is built at startup from the BACKENDS environment variable (comma-separated host:port list). It requires no external library.

You can inspect the current ring distribution:

```
curl http://localhost:8000/ring
```

This returns the number of virtual nodes assigned to each backend, which should be 100 per node.

---

## 4. Containerization

Each component has its own Dockerfile:

- **Dockerfile.kvstore** -- multi-stage build; Go builder compiles a static binary, copied into an Alpine runtime image. No Go toolchain ships in the final image.
- **Dockerfile.proxy** -- same multi-stage pattern for the proxy binary.

**docker-compose.yml** defines three KV nodes (kv1, kv2, kv3) and the proxy. The proxy waits for all three nodes to pass their health checks before starting. Data for each node is persisted to a named Docker volume.

## 6. How to Run

### Start the cluster

```bash
docker compose up --build
```

Ports on the host:

| Service | Port | Description            |
|---------|------|------------------------|
| proxy   | 8000 | Entry point for all ops|
| kv1     | 8081 | Node 1 (direct access) |
| kv2     | 8082 | Node 2 (direct access) |
| kv3     | 8083 | Node 3 (direct access) |

### Manual verification (PowerShell)

```powershell
# Health check (shows all node statuses and total key count)
Invoke-WebRequest -Uri http://localhost:8000/ -UseBasicParsing

# Write a key
Invoke-WebRequest -Uri http://localhost:8000/hello -Method POST -ContentType "application/json" -Body '{"value":"world"}' -UseBasicParsing

# Read it back
Invoke-WebRequest -Uri http://localhost:8000/hello -UseBasicParsing

# Delete it
Invoke-WebRequest -Uri http://localhost:8000/hello -Method DELETE -UseBasicParsing

# See ring distribution
curl.exe http://localhost:8000/ring
```

### Run the benchmark

```bash
pip install requests matplotlib numpy
py benchmark/bench.py
py benchmark/plot.py
```

### Stop the cluster

```bash
docker compose down        # keeps data volumes
docker compose down -v     # also deletes data volumes
```

## 8. Performance Results

The benchmark ran 500 SET operations followed by 500 GET operations at each node count, using 8 concurrent threads. All operations went through the Python consistent hash ring directly to the backend nodes. Zero errors and zero mismatches were recorded across all 1,500 write and 1,500 read operations.

### Throughput

| Nodes | SET (ops/s) | GET (ops/s) |
|-------|-------------|-------------|
| 1     | 180.8       | 1789.3      |
| 2     | 182.5       | 1708.3      |
| 3     | 185.4       | 1675.2      |

### Latency

| Nodes | SET avg (ms) | SET p99 (ms) | GET avg (ms) | GET p99 (ms) |
|-------|--------------|--------------|--------------|--------------|
| 1     | 43.75        | 49.32        | 4.43         | 7.35         |
| 2     | 43.47        | 48.51        | 4.64         | 8.02         |
| 3     | 42.89        | 48.63        | 4.74         | 9.50         |

## 9. Analysis

**Throughput.** SET throughput increases slightly from 180.8 to 185.4 ops/s as nodes are added, because write operations are parallelized across more nodes. GET throughput decreases slightly from 1789.3 to 1675.2 ops/s due to the overhead of maintaining more TCP connections on the same host. On separate physical machines, both SET and GET throughput would scale close to linearly with node count, since each node would have its own dedicated CPU and network interface.

**Latency.** SET latency averages around 43 ms across all configurations. This is dominated by Docker bridge network overhead rather than processing time. GET latency averages around 4 to 5 ms, reflecting fast in-memory reads. The p99 GET latency increases slightly with more nodes (7.35 ms at 1 node, 9.50 ms at 3 nodes) due to connection multiplexing overhead on the shared host.

**Key distribution.** With 100 virtual nodes per backend and 500 keys, the distribution across three nodes was 140 / 204 / 156. This variance (roughly plus or minus 15 percent from the ideal 167) is expected at this scale and converges toward equal thirds as the number of keys grows.

**Correctness.** The consistent hash ring guarantees that the same key always routes to the same node. This was confirmed by the 0 percent mismatch rate on the GET phase: every key written in the SET phase was found on the expected node during reads.

## 10. Challenges and Solutions

**Challenge 1: Docker bridge network latency.** All containers run on the same host, sharing a virtual network. This added approximately 40 ms of overhead per write operation, which is not representative of real hardware. On a real distributed deployment, this latency would be replaced by actual network latency between machines.

**Challenge 2: Proxy reconfiguration for benchmarking.** The original benchmark design restarted the proxy container with a different BACKENDS variable for each node count. This failed due to container naming conflicts and port binding issues. The solution was to implement the consistent hash ring directly in Python and route benchmark requests to the KV node host ports (8081, 8082, 8083) without involving the proxy at all. This also made the hash ring logic easier to validate, since the Python and Go implementations can be compared directly.

**Challenge 3: curl.exe escaping on Windows.** The Windows version of curl.exe does not handle single-quoted JSON bodies in PowerShell the same way bash does. The solution is to use PowerShell's Invoke-WebRequest cmdlet for manual testing, which handles JSON bodies correctly without escaping issues.
